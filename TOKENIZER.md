# Step 8 — the tokenizer in C++

**Complete on the real `facebook/nllb-200-distilled-600M` vocabulary.** The
last Python dependency in the encode path is gone: `nllb.cpp` now turns text
into ids itself, from the vocabulary embedded in the GGUF.

```
[vocab]
  256204 tokens, 514098 merges (hash 0x83b9cb93114cee71, tokenizer.json)
  source tokenizer.json; bos=0 pad=1 eos=2 unk=3
  202 FLORES codes; eng_Latn=256047 deu_Latn=256042
  ok

[tables]  UAX#29 grapheme boundaries
  588 GCB ranges + 156 pictographic, hash 0xb7d03d48911a68cd
  source: THE GGUF (UCD 2026.8.31)
  identical to the compiled-in tables, row for row
  ok

[golden]  ref/manifest.json, with the language code and eos
  9 cases, 0 failed  ok

[corpus]  ref/tokenizer_corpus.txt, pieces only, plus the decode
  237798 cases, 0 id mismatches, 0 decode mismatches  ok

[sweep]   every Unicode codepoint, reduced to one hash
  n=1112063 (expected 1112063), hash 0xe35ee16f4af7337a (expected 0xe35ee16f4af7337a)
  ok

PASS
```

The handoff's gate was "C++ tokenizer ids == the ids in `ref/*.json` for all 9
cases, exact". That is the `[golden]` line and it is green. The other passes
exist because **the nine goldens catch 2 of the 10 plausible tokenizer bugs** —
measured, see "Testing the tests" below.

## The finding that changed the plan: NLLB's tokenizer is BPE

`sentencepiece.bpe.model` means what its name says. `trainer_spec.model_type`
is BPE, and the fast `tokenizer.json` is a `"type": "BPE"` model with **514098
merges** and no unigram scores anywhere.

The handoff had this down as a SentencePiece **Unigram** model, which would
have meant Viterbi over piece log-probabilities. It is not, and the mistake was
load-bearing: the converter has always written a `tokenizer.ggml.scores` array
shaped like Unigram scores, and for a BPE model those numbers are negated merge
ranks. Nothing reads them, and nothing should.

Two consequences:

* There is no Viterbi in `src/nllb-vocab.cpp`. There is a merge loop.
* The merge list was not in the GGUF **at all**, so the vocabulary as written
  before this step could not have driven a tokenizer even in principle. The
  handoff's "the embedded vocab has never been read" was truer than it looked.

---

## The C++ matches HuggingFace's implementation, not sentencepiece's

Every golden in this repo comes from `AutoTokenizer`, i.e. the *fast*
tokenizer, i.e. the `tokenizers` Rust crate and its `spm_precompiled`
dependency. That is not a faithful port of sentencepiece, and the differences
are not cosmetic. Both were confirmed against the real charsmap before a line
of C++ was written.

### 1. The normalizer takes the SHORTEST match, and eats the whole cluster

sentencepiece's `Normalizer` does a longest-match walk. `spm_precompiled` calls
`common_prefix_search()` and takes **`results[0]`** — the shortest match — and
then advances past the entire grapheme cluster whether or not the match covered
it. Their source says, verbatim:

> Future reader. From @Narsil. / Yes, this is weird, / Yes, this seems broken /
> No, I don't know why Google did this.

What it does, checkable by hand against the real model:

| input | HF fast tokenizer | what longest-match would give |
|---|---|---|
| `A` U+0302 U+0300 | `Â` — **the U+0300 is dropped** | `Ầ` |
| `A` U+0300 U+0301 | `À` | — |
| CR LF | **one** space | two spaces |
| U+1E9B U+0323 | `ṡ` | `ṡ` |

The `Ầ` row is the one to keep in mind: the trie *does* contain the three-
codepoint key, and it is never reached, because the two-codepoint key is a
shorter prefix of it.

### 2. The unit of iteration is the UAX#29 grapheme cluster

`normalize_string` walks **grapheme clusters**, and only clusters **under 6
bytes** get the whole-cluster lookup; longer ones fall back to a per-codepoint
walk. So `src/nllb-grapheme-data.h` exists, generated by
`tools/gen_grapheme_tables.py` (588 GCB ranges + 156 Extended_Pictographic
ranges, Hangul LV/LVT computed rather than tabulated).

The 6-byte gate bounds how much this can matter, which is worth knowing before
anyone tries to delete the tables:

* A cluster of 6+ bytes takes the per-codepoint path, which is
  boundary-independent — merging or splitting such clusters changes nothing.
* So boundaries only matter in the short regime, and there they matter a lot.

Enumerating the whole double-array trie says exactly how much. It has **224711
keys**: 4837 single-codepoint, 13546 two-, 205773 three-, 555 four-. Of the
219874 multi-codepoint keys, **2726 are under 6 bytes** — essentially "a base
character plus one or two combining marks". That set is the entire blast
radius, and it is not empty, which is the argument for the tables.

### 3. AddedVocabulary runs before anything else

The 207 added tokens — 4 control tokens, the 202 FLORES codes, `<mask>` — are
cut out of the **raw** input before the normalizer sees it, and each surviving
run is normalized and pre-tokenized **on its own**. That last part is the
non-obvious bit:

```
"x eng_Latn y"  ->  ['▁x', '▁', 'eng_Latn', '▁y']
```

The bare `▁` is the trailing space of the chunk `"x "`, and `▁y` gets its own
`add_prefix_space`. A tokenizer that normalizes the sentence once and then
looks for language codes produces something different.

`<mask>` is the only one that is flagged `lstrip` (it swallows the whitespace
before it) and the only one flagged `normalized` (it is matched in a second
pass, against the *normalized* text). Both are implemented; the flags travel in
the GGUF rather than being hard-coded, and the converter **refuses** any added
token that sets `single_word`, which is the one flag `nllb_vocab` does not
implement.

## The merges are derived, not stored — and the derivation is checked

transformers builds `tokenizer.json`'s merge list from the sentencepiece piece
list with `SentencePieceExtractor.extract(vocab_scores=None)`: for each piece
**in id order**, every split whose two halves are both in the vocabulary, those
splits ordered by `(left id, right id)`.

That depends on nothing but the vocabulary order, which is already in the GGUF.
Reproducing it in Python gives **514098 merges, byte-for-byte identical** to
the 514098 in the real `tokenizer.json`. So the GGUF does not carry ~6 MB of
merge strings; `nllb_vocab_load` rebuilds them.

A derivation that is right today and silently wrong on some future checkpoint
is exactly the kind of thing this project does not ship, so:

* the converter writes `tokenizer.nllb.merges_hash`, an FNV-1a over the merges
  **as HuggingFace serialised them**;
* `nllb_vocab_load` hashes its own derivation the same way and **refuses to
  load** on a mismatch, naming both hashes.

When the source snapshot has no `tokenizer.json`, the converter derives the
merges itself, hashes those, and records
`merges_hash_source = "derived (unverified)"` — the check degrades to
self-consistency and says so in the gate's banner rather than pretending.

### When the derivation does not fit the vocabulary

The derivation is a property of `facebook/nllb-200-*`, not of BPE. A
**language-specific fine-tune that trims or reorders the vocabulary** — the
usual way to shrink a 256204-piece embedding matrix down to one language pair —
reindexes the pieces while HuggingFace keeps the original merge ORDER, filtered.
The derivation is then not wrong, it is inapplicable, which is a different thing
from a broken checkpoint and deserves a different answer than refusing.

So the converter compares, and on a mismatch writes `tokenizer.nllb.merges` —
the list itself, as HuggingFace serialised it. `nllb_vocab_load` prefers that
key when it is present and derives only in its absence; `merges_hash` still
covers the result, checking a transfer instead of a derivation, and
`merges_hash_source` says which of the two happened. `--embed-merges` forces the
list into a file whose derivation *would* have worked, trading ~6 MB of GGUF for
the ~0.4 s the derivation costs at load.

A vocabulary that survives trimming unchanged in ORDER still derives, because
filtering preserves relative id order; it is reordering and insertion that need
the list.

## What the GGUF gained (the file must be RECONVERTED)

| key | what | size |
|---|---|---|
| `tokenizer.ggml.precompiled_charsmap` | SentencePiece's normalizer: a darts-clone double array plus a blob of replacement strings | 237539 B (trie 177152, blob 60383) |
| `tokenizer.nllb.merges_hash` | u64, the checked invariant above | 8 B |
| `tokenizer.nllb.n_merges` | u32 | 4 B |
| `tokenizer.nllb.merges_hash_source` | provenance string | — |
| `tokenizer.nllb.merges` | the merge list, **only** when the derivation does not fit this vocabulary (or `--embed-merges`) | absent on NLLB-200; ~6 MB when written |
| `tokenizer.nllb.added_tokens` | the 207 AddedVocabulary strings | — |
| `tokenizer.nllb.added_flags` | i32 bitfield: 1 single_word, 2 lstrip, 4 rstrip, 8 normalized | — |
| `tokenizer.nllb.gcb_ranges` | UAX#29 Grapheme_Cluster_Break, as (lo, hi, prop) triples | 7056 B |
| `tokenizer.nllb.extpict_ranges` | Extended_Pictographic, as (lo, hi) pairs | 1248 B |
| `tokenizer.nllb.ucd_version` | which Unicode release those came from | — |

A GGUF converted before step 8 has none of these and is **refused at load**
with a message naming the missing key and telling you to re-run the converter.
That is deliberate: without the charsmap, `ﬁ` never becomes `fi`, `½` never
becomes `1⁄2`, NBSP never becomes a space, and the ids diverge from the goldens
on any input that is not plain ASCII — silently, and only on the inputs nobody
tests.

The converter also now **asserts the shape of the HF normalizer stack**. It
expects exactly `[Precompiled, Replace(" {2,}" -> " ")]` and a
`Metaspace(U+2581)` pre-tokenizer, and exits if it finds anything else, because
`nllb_vocab` implements that stack and nothing else.

## One file, everything in it

The point of the whisper.cpp comparison is that you ship a *file*, not a file
plus a directory of tokenizer JSON. That holds here: the vocabulary, the
charsmap, the added tokens and the grapheme tables are all in the GGUF, and
`nllb_vocab_load` opens it `no_alloc = true` and reads metadata only — so
pointing it at the 2.46 GB checkpoint costs the same as pointing it at the
6.7 MB vocab-only file. Nothing at runtime reads `tokenizer.json`,
`sentencepiece.bpe.model`, or a second GGUF.

The grapheme tables were the last hold-out and were moved in deliberately.
They are **not** a property of the model — every SentencePiece checkpoint would
carry the same ~8 KB — but they *are* a property of the ids, because a cluster
boundary that moves moves the tokenization. Left compiled into the binary, ids
are a function of `(the GGUF, whichever Unicode release you happened to build
against)`; baked into the file, they are a function of the GGUF alone. That is
the property "self-contained" is actually reaching for.

The loader prefers the file's tables and falls back to
`src/nllb-grapheme-data.h` when they are absent, so a GGUF written by some
other tool still works. `[tables]` says which of the two it used, and when they
disagree it does not simply report the row counts — it re-runs the whole corpus
under the compiled-in tables and reports **how many ids actually move**. On the
deliberately damaged file (`--break=gcb`, every `Extend` range deleted) that is
1013 of 237798; on a legitimate UCD bump it may well be zero, and the pass says
so rather than going red on a difference that costs nothing.

What is still in the binary and cannot move: the algorithm — the shortest-match
rule, the 6-byte cluster gate, Metaspace, the BPE loop — and the
`Replace(" {2,}", " ")` normalizer rule. The converter asserts the shape of
HuggingFace's normalizer stack at conversion time, so a checkpoint whose
normalizer is not `[Precompiled, Replace]` is refused rather than silently
tokenized by the wrong rules.

Two keys are written and never read: `tokenizer.ggml.scores` (1.02 MB) and
`tokenizer.ggml.token_type` (1.02 MB). `scores` is the Unigram-shaped array
that turned out to mean negated merge ranks — the exact confusion that cost
this project seven steps — and `token_type` was superseded by `added_flags`.
Both stay because they are llama.cpp-convention keys that generic GGUF tooling
expects, and 2 MB is 0.08% of the f32 file.

## The gate

`tests/test_tokenizer.cpp` → `nllb-test-tokenizer`. Five passes, no tolerance
anywhere — ids are right or wrong. What replaces the tolerance is a bisect: on
a mismatch it prints the normalized string, the Metaspace words and the
per-word ids, so a normalizer bug and a BPE bug do not look alike.

| pass | input | what only it can catch |
|---|---|---|
| `[vocab]` | the GGUF | the merge hash, the 202 codes, `<s>/<pad>/</s>/<unk>` at 0/1/2/3 — the classic fairseq-offset bug |
| `[tables]` | the GGUF | where the grapheme tables came from, and — when the file's and the binary's disagree — how many ids that actually moves |
| `[golden]` | `ref/manifest.json` | the `[src_lang] … [eos]` wrapping, against the same ids the ENCODER goldens were built from |
| `[corpus]` | `ref/tokenizer_corpus.txt` | 237798 cases: normalization, graphemes, added tokens, and the **decode** |
| `[sweep]` | `ref/tokenizer_sweep.txt` | one hash over every one of the 1112063 codepoints — the C++ matching something the reference leaves alone |

A pass whose input file is missing is a **FAILURE**, not a skip. Step 4 shipped
the opposite and deleting 8 of 9 goldens still printed PASS. `--no-golden`,
`--no-corpus`, `--no-sweep` make leaving one out deliberate and visible.

Two new tools, neither needing torch or the 2.46 GB of weights:

* `tools/dump_tokenizer_reference.py` — writes the corpus and the sweep from a
  `tokenizer.json`. 9 encoder prompts + 32 pinned quirks + 220373 charsmap
  probes (every codepoint whose lead byte the trie accepts) + 20000
  deterministic fuzz.
* `tests/make_vocab_gguf.py` — a **6.7 MB vocab-only GGUF** in about a second,
  through the converter's own `load_vocab()` so there is one code path and not
  two. `nllb-test-tokenizer` takes it happily; every other binary refuses it
  for want of tensors, which is the intended division.

### The Python prototype came first

`src/nllb-vocab.cpp` was written from a pure-Python reimplementation that was
first made exact against the `tokenizers` library, so that no C++ was ever
debugged against two unknowns at once. That prototype was clean on: 20000
random strings, **all 1112063 codepoints**, all 14676 multi-codepoint trie keys
in five variants each (alone, `+U+0301`, `+x`, `x+`, `+U+0301U+0323`), and 3291
base×combining-mark pairs. Zero divergences before the first line of C++.

## Testing the tests

`tests/corrupt_gguf.py` damages a tensor. The tokenizer has no tensors — its
failure modes are in the algorithm — so `tests/corrupt_tokenizer.py` mutates
the source instead, compiling each mutation into `/tmp` and running the gate
against it. Every mutation is a *plausible implementation*: the one you would
write having read sentencepiece rather than `spm_precompiled`, or codepoints
rather than graphemes.

| mutation | golden | corpus | sweep |
|---|---|---|---|
| longest trie match (sentencepiece's rule) | **pass** | FAIL | FAIL |
| codepoints instead of grapheme clusters | **pass** | FAIL | FAIL |
| Metaspace without `add_prefix_space` | FAIL | FAIL | FAIL |
| one unk per character instead of per run | **pass** | FAIL | FAIL |
| no AddedVocabulary | **pass** | FAIL | FAIL |
| highest-ranked merge first | FAIL | FAIL | FAIL |
| equal-rank ties to the rightmost position | **pass** | FAIL | FAIL |
| drop `Replace(" {2,}" -> " ")` | **pass** | FAIL | FAIL |
| ignore `lstrip` on `<mask>` | **pass** | FAIL | FAIL |
| split merge candidates at every byte | *inert — see below* | | |

**The nine goldens catch 2 of 9.** That is the number to remember before anyone
calls `[corpus]` and `[sweep]` redundant. Nine sentences of ordinary prose
cannot exercise a 224711-entry normalizer trie, and seven of these nine
mutations produce identical ids on all nine of them.

The tenth is inert and is kept for what it says: splitting merge candidates at
byte boundaries rather than character boundaries changes nothing, because a
split that lands mid-character produces a substring that is not valid UTF-8 and
is therefore never in the vocabulary. The boundary test is a speed
optimisation, not a correctness requirement. If that row ever starts being
caught, something has changed about the vocabulary.

Five data corruptions, via `tests/make_vocab_gguf.py --break=...`, all refused
at load with a specific message:

| break | what the loader says |
|---|---|
| `charsmap` | "no `tokenizer.ggml.precompiled_charsmap` … converted before step 8" |
| `hash` | "merge derivation mismatch: rebuilt 514098 merges hashing to 0x…, GGUF says 0x…" |
| `shift` (rotate the vocab by one) | "added token `<mask>` is not in the vocabulary" |
| `added` | "no `tokenizer.nllb.added_tokens` … converted before step 8" |
| `single-word` | "added token `<s>` sets single_word, which this tokenizer does not implement" |
| `gcb` (drop every Extend range) | not refused — legal data. `[tables]` prices it at **1013 of 237798 cases moved** and `[corpus]` fails with the bisect: `Â` becomes `A` `◌̂` `◌̀`, three tokens instead of one |
| `tables` (omit them entirely) | not refused — falls back to the compiled-in header, passes, and says the file is not self-contained |

Note the `shift` row: the added-token resolution catches the fairseq-offset bug
*before* the merge hash gets a chance to, because it runs first. Both would
have caught it.

## Numbers

Sandbox, x86, `-O2`, real 256204-token vocabulary:

| | |
|---|---|
| `gguf_init_from_file`, metadata only | 44 ms |
| vocabulary + merge derivation | 476 ms |
| tokenizing a 44-character sentence | **27 µs** |
| vocab-only GGUF on disk | 6.7 MB |
| charsmap in the GGUF | 237539 B |

The 476 ms is one-off process startup and is dominated by hash-map
construction: 256204 string keys, 256204 view keys, 514098 merge entries.
Against loading 1.24 GB of f16 weights it is noise, and for `nllb-cli` it will
be the difference between 0.5 s and 0.0 s before the first token. The lever, if
it ever matters, is to store the merges rather than derive them — which trades
this for ~6 MB of file and 514098 GGUF string reads, and is not obviously a
win. Measure before changing it.

## Proven vs not proven

**Proven.** The C++ tokenizer reproduces HuggingFace's `NllbTokenizerFast`
exactly on the real 256204-token NLLB vocabulary: the 9 encoder golden prompts
with their `[eng_Latn] … [</s>]` wrapping; 237798 corpus cases covering
normalization, grapheme clustering, added tokens and the round trip back to
text; and every one of the 1112063 Unicode codepoints. The merge list derived
from the vocabulary order is byte-identical to the 514098 merges HuggingFace
serialised. Nine of nine non-inert source mutations turn the gate red.

**Not proven.**

* **Any tokenizer other than this one.** Everything here is pinned to NLLB's
  `tokenizer.json`. The `sentencepiece.bpe.model`-only path in the converter is
  written and **has never run** — no `.model` file was available — so its
  charsmap extraction and its unverified merge hash are untested code.
* **`single_word` added tokens.** Not implemented; converter and loader both
  refuse rather than guess. NLLB has none.
* **Text longer than a sentence.** The BPE merge loop is a heap over a linked
  list, so it is O(n log n) rather than the prototype's O(n²), but nothing in
  the corpus is longer than a few hundred bytes. A whole document in one
  `▁`-free run is untested.
* **The Unicode version.** `src/nllb-grapheme-data.h` is generated from the
  `regex` package's UCD; `tokenizers` uses `unicode-segmentation`'s. They agree
  on everything the corpus and sweep touch. A newer UCD could move a cluster
  boundary — which is why `ci.yml` now asserts the committed header still
  matches its generator, and why the tokenizer gate must be re-run after any
  regeneration.
* **Decode of ids the model produced.** `nllb_vocab_decode` is checked against
  `tokenizer.decode(..., skip_special_tokens=True)` on the corpus, but every
  one of those id sequences came from encoding. Decoding arbitrary model output
  — in particular byte-fallback pieces, which NLLB's vocabulary does not have —
  is not covered.
* **Anything about the model.** This gate compares text to ids. It says nothing
  about whether those ids translate correctly; `nllb-test` and
  `nllb-test-generate` own that.

## New traps

21. **`sentencepiece.bpe.model` is BPE.** Not Unigram, despite the file being
    the same shape as XLM-R's. There are no log-probabilities and there is no
    Viterbi. The `tokenizer.ggml.scores` array the converter writes is
    Unigram-shaped and meaningless here; nothing reads it.

22. **The reference is HuggingFace's implementation, not sentencepiece's.**
    `spm_precompiled` takes the **shortest** trie match and consumes the whole
    grapheme cluster on a hit. Porting sentencepiece's `Normalizer` instead
    gives a tokenizer that is right on ASCII, right on most prose, and wrong on
    `CR LF` and on any base character carrying two combining marks. The golden
    nine do not contain one.

23. **Grapheme clusters, but only under 6 bytes.** The whole-cluster lookup is
    gated on `grapheme.len() < 6`; everything longer degrades to a
    per-codepoint walk where boundaries are irrelevant. So UAX#29 has to be
    right exactly where clusters are short — base plus combining marks — and
    the 2726 sub-6-byte multi-codepoint trie keys are the entire set of inputs
    that can distinguish a correct implementation from a naive one.

24. **AddedVocabulary splits BEFORE normalization, and each chunk is
    pre-tokenized separately.** `add_prefix_space` therefore fires once per
    chunk, not once per sentence, which is why `"x eng_Latn y"` contains a bare
    `▁` token. And `<mask>` — the only `lstrip` token — eats the space before
    it and not the one after.

25. **The merge list is derivable from the vocabulary order, and that is an
    assumption until something checks it.** `tokenizer.nllb.merges_hash` is
    that check. Do not remove it as redundant: it is the only thing standing
    between a future checkpoint whose `tokenizer.json` was built by a different
    transformers version and a tokenizer that is subtly wrong for the rest of
    its life.

26. **The grapheme tables are in the GGUF, and the binary's copy is only a
    fallback.** Ids are meant to be a function of the file alone. If you
    regenerate `src/nllb-grapheme-data.h` on a newer Unicode release, existing
    GGUFs keep their own tables and keep tokenizing exactly as before — which
    is the point — and `[tables]` will report the two as DIFFERING and price
    the difference in ids. That is a report, not a failure, unless ids actually
    move. What would be a failure is deleting the file's tables and assuming
    the binary's are equivalent; `--break=gcb` exists to show they need not be.

## Commands

```bash
# a vocab-only GGUF - no weights, ~1 second, 6.7 MB
python tests/make_vocab_gguf.py models/nllb-600M models/nllb-vocab.gguf

# the corpus and the every-codepoint sweep. No torch.
python tools/dump_tokenizer_reference.py models/nllb-600M --out ref/ \
    --src-lang eng_Latn --fuzz 20000

# the gate. Point it at the vocab-only file or at the real checkpoint.
./build/bin/nllb-test-tokenizer models/nllb-600M-f32.gguf ref/ -v

# one string, every stage printed - the first thing to run on a mismatch
./build/bin/nllb-test-tokenizer models/nllb-vocab.gguf \
    --text "Zwölf Boxkämpfer jagen Eva quer über den großen Sylter Deich."

# does the gate actually fire? ~50 s, ten source mutations.
python tests/corrupt_tokenizer.py build models/nllb-vocab.gguf ref/

# the data side: a corrupted grapheme table must turn it red, and a file with
# no tables at all must fall back to the compiled-in header and still pass.
python tests/make_vocab_gguf.py --break=gcb    models/nllb-600M /tmp/bad.gguf
python tests/make_vocab_gguf.py --break=tables models/nllb-600M /tmp/none.gguf
./build/bin/nllb-test-tokenizer /tmp/bad.gguf  ref/     # expect FAIL
./build/bin/nllb-test-tokenizer /tmp/none.gguf ref/     # expect PASS

# regenerate the Unicode tables (then RE-RUN THE GATE). This changes only the
# BINARY's fallback copy; existing GGUFs carry their own and are unaffected.
pip install regex
python tools/gen_grapheme_tables.py > src/nllb-grapheme-data.h
```

`[golden]` needs `ref/manifest.json`, which comes from `tools/dump_reference.py`
and therefore from torch. The other three passes need only `tokenizer.json`.
